AI 코딩 에이전트를 본격적으로 쓰기 시작하면, 어느 순간 토큰 청구서가 조용히 불어나 있는 걸 발견한다. 그리고 대부분은 여기서 **한 가지 요령**에 기댄다. "프롬프트를 잘 쓰자", "컨텍스트를 줄이자" 같은 것.

그런데 몇 달 써보고 내린 결론은 이렇다. **토큰은 한 곳에서 새지 않는다.** 새는 지점이 최소 세 군데이고, 각 지점은 원인이 달라서 하나만 막으면 나머지 둘에서 계속 흘러나간다. 이 글은 그 세 구멍을 각각 막는 오픈소스 도구 세 개 — **Ponytail, Graphify, Headroom** — 를 하나의 파이프라인으로 묶어 정리한 것이다.

## 토큰이 새는 세 지점

에이전트가 토큰을 태우는 과정을 뜯어보면 이렇게 나뉜다.

1. **생성** — 애초에 코드를 너무 많이 짠다. 날짜 입력 하나에 404줄짜리 커스텀 컴포넌트를 만든다. 짠 만큼 출력 토큰이고, 그걸 다시 읽는 만큼 입력 토큰이다.
2. **재읽기** — 같은 파일을 몇 번이고 다시 `grep`하고 읽는다. 대화가 길어질수록 컨텍스트가 매번 파일 내용으로 채워진다.
3. **원문** — 도구 출력·로그·RAG 청크가 **가공 없이 통째로** LLM에 들어간다. JSON 응답 하나가 수천 토큰을 먹는다.

핵심은 이 셋이 **서로 다른 계층의 문제**라는 것이다. 그래서 도구도 따로다.

| 계층 | 문제 | 도구 | 대표 수치 |
|---|---|---|---|
| **생성**(행동) | 코드를 너무 많이 씀 | **Ponytail** | 코드 −54%, 토큰 −22% |
| **재읽기**(검색) | 파일을 반복해서 읽음 | **Graphify** | 그래프 생성 LLM 크레딧 0 |
| **원문**(압축) | 읽는 것이 통째로 들어감 | **Headroom** | JSON −60~95%, 코딩 −15~20% |

아래에서 각 계층을 하나씩 본다.

## 1. Ponytail — 애초에 덜 짜게 만든다

가장 싼 토큰은 **처음부터 안 쓴 코드**다. 생성 단계에서 코드량 자체를 줄이면 그 뒤의 모든 비용(리뷰·재읽기·수정)이 같이 줄어든다.

[Ponytail](https://github.com/DietrichGebert/ponytail)은 에이전트를 "오버엔지니어링하지 않는 게으른 시니어"처럼 행동하게 만드는 스킬이다. 핵심 장치는 **게으름 사다리**. 문제를 *이해한 뒤*, 처음 성립하는 칸에서 멈춘다.

```text
1. 존재할 필요가 있나?       → 없으면 스킵 (YAGNI)
2. 이미 코드베이스에 있나?    → 재사용, 재작성 금지
3. 표준 라이브러리로 되나?    → 사용
4. 네이티브 플랫폼 기능인가?  → 사용  (예: <input type="date">)
5. 설치된 의존성으로 되나?    → 사용
6. 한 줄이면 되나?           → 한 줄
7. 그제야                     → 작동하는 최소한
```

이게 왜 중요하냐면, 에이전트의 기본 성향이 "요청받으면 뭐라도 만든다"이기 때문이다. 날짜 선택기를 요청하면 접근성·키보드 내비게이션·로케일까지 챙긴 404줄짜리 컴포넌트를 만든다. 하지만 사다리 4번을 돌면 `<input type="date">` 한 줄로 끝난다. 실제 사례에서 **404줄 → 23줄**로 줄었다.

수치도 이 지점에서 나온다. FastAPI + React 오픈소스 레포를 헤드리스로 수정한 실측(12개 기능 티켓, Haiku 4.5)에서 스킬 유무만 다른 동일 에이전트를 비교했더니:

- **코드 −54%**(최대 −94%), **토큰 −22%**, **비용 −20%**, **시간 −27%**
- 그러면서 **안전 가드를 100% 유지한 유일한 방식**

여기서 오해하면 안 되는 게 있다. **게으르되 부주의하지 않다.** 신뢰 경계 검증, 데이터 손실 처리, 보안, 접근성은 **절대 생략하지 않는다.** "해법에는 게으르되, **읽기에는 절대 게으르지 않다**" — 변경이 닿는 코드를 먼저 읽고 흐름을 추적한 뒤에 사다리를 돈다. 이해를 건너뛰는 게 아니라, 이해한 다음 과잉을 걷어내는 것이다.

도입이 가장 쉽다는 것도 장점이다. 인프라를 안 건드리고 **행동만** 바꾸므로 플러그인 설치 한 번이면 된다.

```text
/plugin marketplace add DietrichGebert/ponytail
/plugin install ponytail@ponytail
```

한 가지 현실적인 단서: 절감폭은 **오버빌드 함정에서 크고**, 이미 최소한으로 짜인 작업에선 0에 가깝다. 마법이 아니라 "안 짜도 될 걸 안 짜는" 것이다.

## 2. Graphify — 같은 파일을 다시 읽지 않게 한다

레포가 커지면 에이전트는 매번 `grep`으로 뒤지고 파일을 열어 읽는다. 그 재읽기가 전부 입력 토큰이다. 대화가 길어질수록, 그리고 코드베이스가 클수록 이 비용이 지수적으로 커진다.

[Graphify](https://github.com/Graphify-Labs/graphify)는 접근을 바꾼다. 프로젝트 전체(코드·문서·PDF·이미지·영상)를 **한 번 지식 그래프로 매핑**해두고, 이후엔 파일을 읽는 대신 **그래프를 질의**하게 한다. `/graphify .` 한 번이면 매핑이 끝난다.

설계가 영리한 지점이 셋 있다.

- **로컬·결정적** — 코드는 tree-sitter AST로 파싱한다. LLM을 안 쓰고(외부 유출 없음, ~40개 언어), 그래서 **그래프 생성에 드는 LLM 크레딧이 0**이다. (문서·PDF·미디어만 모델 semantic pass를 쓴다.)
- **근거 태그** — 모든 엣지에 `EXTRACTED`(원문에 명시) vs `INFERRED`(그래프가 추론) 라벨이 붙는다. "직접 읽은 사실"과 "추론한 연결"을 구분할 수 있다.
- **벡터 인덱스가 아님** — 임베딩·벡터스토어 없이 실제로 순회하는 그래프다.

질의는 이렇게 한다.

```bash
graphify explain "APIRouter"            # 한 개념의 연결·근거 설명
graphify path "FastAPI" "ModelField"    # 두 개념 간 최단 경로
graphify query "<자연어 질문>"           # 질문에 맞는 부분 그래프만 반환
```

산출물은 세 개다. 브라우저에서 노드를 클릭·필터하는 `graph.html`, 핵심 개념과 의외의 연결을 정리한 `GRAPH_REPORT.md`, 그리고 재읽기 없이 언제든 질의하는 `graph.json`. 여기에 **God nodes**(가장 많이 연결된 개념), **커뮤니티 분할**(Leiden 알고리즘, LLM 없이 서브시스템 라벨링), `calls`/`imports`/`inherits` 같은 교차 파일 링크까지 제공한다.

벤치마크상 그래프 생성 LLM 크레딧은 0이면서 LongMemEval-S에서 QA 정확도 76%로 dense RAG와 동급을 냈다. 그리고 개인적으로 가장 흥미로운 지점 — **Obsidian 볼트와 궁합이 특히 좋다.** 영속 메모리 세팅과 붙이면 세션당 토큰 절감폭이 크게 벌어진다는 보고가 있다. 노트를 Obsidian으로 관리하는 사람이라면 이 조합을 눈여겨볼 만하다.

```bash
uv tool install graphifyy      # PyPI 패키지명은 graphifyy — y가 두 개다
graphify install               # AI 어시스턴트에 스킬 등록
# 이후 어시스턴트에서: /graphify .
```

## 3. Headroom — 그래도 들어가는 건 압축한다

Ponytail로 덜 짜고 Graphify로 덜 읽어도, **결국 LLM에 들어가는 텍스트**는 남는다. 도구 출력, 로그, 남은 파일, 대화 이력. [Headroom](https://github.com/headroomlabs-ai/headroom)은 이 모든 걸 **LLM에 닿기 전에 압축**한다. 슬로건이 정확하다. "같은 답, 토큰은 일부만."

동작은 이렇다. 콘텐츠 타입을 감지해 알맞은 압축기로 보낸다 — JSON은 SmartCrusher, 코드는 AST 기반 압축기, 텍스트는 전용 모델(Kompress). 그리고 원본은 **로컬에 보관해두고 LLM이 필요할 때만 복원**하는 가역 압축(CCR)이다. 즉 정보를 버리는 게 아니라, 당장 필요 없는 형태를 접어두는 것이다.

가장 매력적인 건 **코드 수정 0**으로 붙일 수 있다는 점이다. 형태가 다섯 가지나 된다 — 라이브러리 인라인 호출, 언어 무관 프록시, 에이전트 래핑, MCP 서버, 크로스-에이전트 공유 메모리. 그중 래핑이 제일 간단하다.

```bash
uv tool install --python 3.13 "headroom-ai[all]"
headroom wrap claude       # 기존 세션을 그대로 감싼다
headroom dashboard         # 실시간 절감 확인
```

절감폭은 **JSON −60~95%, 코딩 전반 −15~20%**. 출력 토큰까지 줄여주는데, 모델이 되받아 쓰는 반복 코드·의례적 문구를 줄이기 때문이다.

다만 **정직하게 짚어야 할 반론**이 있다. 커뮤니티 A/B 벤치마크(`jinseo-jang/headroom-claude-code-benchmark`)는 "실제 절감의 상당수는 프록시가 아니라 `ENABLE_TOOL_SEARCH`에서 온다"고 주장한다. 즉 절감의 출처가 우리가 생각한 곳이 아닐 수 있다. **자체 환경에서 A/B로 측정한 뒤 도입하자.** 이건 Headroom만의 문제가 아니라 이 글의 세 도구 모두에 해당하는 원칙이다.

## 세 계층을 쌓으면: 경쟁이 아니라 보완

여기까지 왔으면 눈치챘겠지만, 세 도구는 **겹치지 않는다.** 각자 다른 계층을 맡으니 함께 쓰면 절감이 **중첩**된다.

```text
사용자 요청
   │
   ▼  ① Ponytail   생성 단계에서 코드·출력량 자체를 축소
   │
   ▼  ② Graphify   파일 재읽기 → 그래프 질의로 입력 토큰 축소
   │
   ▼  ③ Headroom   남은 입력·출력을 프록시/라이브러리에서 압축
   │
   ▼  LLM
```

**덜 만들고(Ponytail) → 덜 읽고(Graphify) → 남은 걸 압축한다(Headroom).** 한 계층만 막으면 다른 계층에서 계속 새기 때문에, 스택으로 쌓을 때 진가가 나온다. 예를 들어 Ponytail이 코드를 절반으로 줄여도 그 절반을 반복해서 다시 읽으면 입력 토큰은 여전히 크고, Graphify가 재읽기를 없애도 도구 출력 JSON이 통째로 들어가면 원문에서 샌다.

## 어디부터 도입할까

난이도(=손대는 범위) 순으로 붙이는 걸 권한다.

1. **Ponytail** — 인프라 무변경, 행동만 바뀜. 플러그인 설치 한 번. **가장 손 안 대는 시작점.**
2. **Graphify** — 레포가 크고 파일 재읽기가 많다면. Obsidian 볼트를 쓰면 특히 이득.
3. **Headroom** — 입력/출력 자체를 강하게 압축하고 싶을 때. 프록시/래핑으로.

한 번에 셋을 다 붙이지 말고, 하나씩 올리면서 **각 단계의 절감을 따로 측정**하는 게 좋다. 그래야 어느 계층이 내 워크로드에서 실제로 효과가 있는지 안다.

## 측정에 관한 정직한 노트

벤치 수치는 참고일 뿐, 내 환경에서 재현되리란 보장은 없다.

- **Ponytail**의 절감은 오버빌드 상황에서 크고, 이미 최소한인 코드에선 거의 0이다.
- **Headroom**은 위 반론처럼 진짜 원인이 다른 설정일 수 있으니 A/B가 필수다.
- **Graphify**는 코드가 바뀌면 그래프 재생성이 필요하다(단, 생성 비용이 LLM 크레딧 0이라 부담은 작다).

공통 원칙은 하나다 — **도입 전후를 같은 작업으로 재보라.** 토큰·비용·시간뿐 아니라 **결과 품질(안전 가드·정확도)** 이 유지되는지까지 봐야 한다. 싸졌는데 틀리면 아낀 게 아니다.

## 마무리

토큰은 한 곳에서 새지 않는다. 너무 많이 만들고(생성), 같은 걸 다시 읽고(검색), 읽은 걸 통째로 넣는다(원문). Ponytail·Graphify·Headroom은 각각 그 세 구멍을 막는 도구이고, **경쟁이 아니라 계층 보완**이라 함께 쌓을수록 효과가 커진다.

하나만 고른다면 **Ponytail**로 시작하되, 결국 정공법은 **세 계층을 모두 보는 것**이다. 요령 하나가 아니라, 파이프라인으로 접근하자.
